## 1. UI 界面架构需求（双模式双端设计）

系统必须同时提供两种形态的界面：**Client UI（面向普通本科学生）** 与 **Debug UI（面向开发者调试与极客排查）**。两者共享底层同一套状态机与版本存储。

```
                       ┌───────────────────────────────────────┐
                       │          LangGraph StateGraph         │
                       │     (Core Multi-Agent Execution)      │
                       └───────────────────┬───────────────────┘
                                           │ WebSocket / SSE
                 ┌─────────────────────────┴─────────────────────────┐
                 ▼                                                   ▼
┌─────────────────────────────────┐                 ┌─────────────────────────────────┐
│           Client UI             │                 │            Debug UI             │
│   (面向学生: 极简Agent交互)      │                 │  (面向开发者: 类 n8n 节点工作台)  │
├─────────────────────────────────┤                 ├─────────────────────────────────┤
│ • 单一轻量交互输入框            │                 │ • 可视化工作流拓扑画布 (Graph)   │
│ • 智能拖拽上传 (模板/批注论文)  │                 │ • 实时执行链路流光动效 (Trace)   │
│ • 执行态动态加载卡片与呼吸动效  │                 │ • 节点运行次数/耗时/Token度量   │
│ • Docx 版本演进数轴与下载操作   │                 │ • 节点 State 输入输出抽屉检查器 │
│ • 论文修改说明书 (Changelog)   │                 │ • 同步集成 Docx 版本节点与数轴  │
└─────────────────────────────────┘                 └─────────────────────────────────┘
```

### 1.1 Client UI（客户端 / 面向普通学生用户）
- **设计目标**：零使用门槛、无冗余设置，如同与专属论文导师交流，界面聚焦于“输入任务 $\rightarrow$ 观察进展 $\rightarrow$ 查看/下载不同版本成果”。
- **核心组件功能**：
  1. **智能交互输入框（Agent Input Bar）**：
     - 支持纯文本输入（毕业设计选题、补充要求、文本修改意见）。
     - 支持直接拖拽上传文件：
       - 创作模式：拖入学校 `.docx` 模板文件。
       - 编辑模式：拖入待修改的 `.docx` 文件，或导师红笔批改截图（图片格式）。
     - 模式自适应切换（自动检测是否上传了已有论文决定进入创作模式或编辑模式，亦可手动切换“✨ 创作新论文” / “✏️ 修改旧论文”）。
  2. **任务流式执行态动画（Agent Execution Animation）**：
     - 拒绝单调静态百分比进度条。采用现代 Agent 执行卡片流与脉冲呼吸动效：
       - 阶段卡片动态点亮：`[解析学校模板 100%] -> [规划三级大纲中...] -> [生成系统架构图...] -> [装配排版中...]`。
       - 实时显示当前正在工作的 Agent 思考气泡（如：“*正在为第4章绘制业务时序图*”、“*正在检索中国知网/IEEE相关参考文献*”）。
  3. **Docx 版本演进数轴与时间树（Timeline & Version Nodes）**：
     - 在界面右侧或底部展示**横向/纵向版本时间数轴**：
       - 每一个节点代表一次成稿产出（如：`v1.0 初稿生成 (13,420字)`、`v1.1 针对第3章批注修改 (14,100字)`）。
       - 节点标有清晰的时间戳、触发原因标签。
       - **交互操作**：
         - 📥 **一键下载**：直接导出该版本的 `.docx`。
         - 👁️ **在线预览**：可在线翻页查看该版本的无损高清页面截图。
         - 📋 **修改对比报告**：点击版本间的连接线，即时弹出《修改对照清单》（说明修改了哪些小节、新增了什么图表、如何逐条响应导师批注）。
         - ⏪ **版本回滚/分叉（Fork/Rollback）**：点击任意历史节点，可选择“回滚至此版本”或“以此版本为基础提出新修改”。

### 1.2 Debug UI（调试工作台 / 面向开发者与调试分析）
- **设计目标**：参考 **n8n / ComfyUI / Langflow / Dify** 的节点式可视化编排与可观测性界面，能够全面监控 LangGraph 的内部运行机制。
- **核心组件功能**：
  1. **可视化工作流画布（Workflow DAG Canvas）**：
     - 基于 React Flow / Vue Flow 渲染 LangGraph 的完整有向图拓扑结构：展示所有状态节点（State Nodes）、条件分支路由（Conditional Edges）、子图（Subgraphs）。
     - 支持拖拽平移、缩放、按层次自动排版。
  2. **运行时链路动态高亮与流行动效（Active Trace & Flow Animation）**：
     - 当后台任务运行时，工作流当前正在执行的节点呈现高亮光环与呼吸脉冲（Glowing Pulse）。
     - 数据流在连线上呈现粒子流动动画，清晰看到数据从哪一流向哪一节点。
     - 执行成功的节点显示绿色对勾，出错节点显示红色警报，反思重试回路（Reflection Loop）呈现回环光效。
  3. **节点运行度量与计数看板（Node Metrics & Execution Counters）**：
     - 每个节点右上角常驻徽标（Badge）：
       - **运行次数（Execution Count）**：清晰显示该节点在此次任务中被触发了多少次（例如：分章起草节点执行了 6 次、校验反思节点重试了 2 次）。
       - **累计耗时（Duration / Latency）**。
       - **Token 消耗统计**（Prompt Tokens / Output Tokens / 预估调用成本）。
  4. **节点状态检查抽屉（State Inspector Drawer）**：
     - 点击画布上的任意节点，屏幕右侧滑出详细检查面板：
       - **Input State**：查看进入该节点时的全局状态快照（JSON 格式，包含当前已生成的目录大纲、实体字典等）。
       - **Prompt & LLM Calls**：查看该节点拼装的具体 Prompt 和大模型原始回复。
       - **Output Delta**：查看该节点向 LangGraph 全局状态更新了哪些字段（State Update）。
       - **Terminal / Logs**：查看该节点调用的底层命令行输出（stdout / stderr）。
  5. **集成 Docx 版本数轴联动（Integrated Version Timeline）**：
     - 画布底部嵌入相同的 Docx 版本时间轴。
     - 点击时间轴上的某个版本节点（如 `v1.1`），工作流画布将**高亮复现**生成该版本所激活的完整执行子路径，极大方便开发者对比不同版本的执行轨迹与排查问题。

## 2. `docx-skill` 现有能力深度遍历与二次开发扩展需求

### 2.1 原生 `docx-skill` 现状遍历与局限分析
通过对系统中现有 `docx-skill`（位于 `config/skills/docx/`）的源代码与规范进行深入排查，其现状如下：

| 原生已有能力 | 技术实现方式 | 在高校本科论文场景下的致命局限 |
| :--- | :--- | :--- |
| **新建空文档** | `docx-js` (npm) | **只能全新创建，无法打开或编辑用户学校的已有模板**。若用它从零重画，学校特定的封面排版、下划线、印章占位符会全部变形。 |
| **编辑现有文档** | `unzip` $\rightarrow$ XML 正则/文本替换 $\rightarrow$ `zip` | **脆弱且极易损坏文档**。对于跨多页结构、新增复杂章节、插入带关系的图片极为吃力，无法做到结构化 AST 操作。 |
| **合并 Text Runs** | `merge_runs.py` | 仅做连续相同格式 run 的合并，无语义理解能力。 |
| **添加 Word 批注** | `comment.py` | **单向写入（只写不读）**。**无法解析提取**导师已在 Word 中写好的批注内容及其在文中的精确定位。 |
| **接受修订** | `accept_changes.py` | 依赖系统安装了 LibreOffice，只能全盘无脑接受所有修订，无法结构化分析修改了哪些字句。 |
| **基础三线表** | `three_line_table.py` | 只对已有表格替换上下边框，未处理**跨页断行 (`cantSplit`)** 和**跨页表头重复 (`tblHeader`)**，打印或导出时表格易截断。 |
| **交叉引用与角标** | `SKILL.md` 提及 `BookmarkStart` 与 `SimpleField` | 仅为 `docx-js` 的纯脚本代码片段，**缺少从正文自动抽取图表、计算章节编号、构建书签和引用域的完整自动化管线**。 |

### 2.2 二次开发与扩展功能规划清单（Extensions Matrix）

基于上述局限，必须在原有 docx-skill 基础上研发以下 6 大二次开发核心扩展模块：

```
                    ┌─────────────────────────────────────────────────┐
                    │        系统专用的 docx 扩展核心库                 │
                    │        (custom_docx_extensions/)                │
                    └────────────────────────┬────────────────────────┘
                                             │
      ┌───────────────────┬──────────────────┼───────────────────┬───────────────────┐
      ▼                   ▼                  ▼                   ▼                   ▼
【模块1: 模板双轨引擎】 【模块2: 交叉引用编译器】 【模块3: 批注双向解析器】 【模块4: 学术三线表强化】 【模块5: 语义Diff比对器】
  template_slicer      cross_ref_engine     comment_parser      academic_table       docx_semantic_diff
  • 静态保留页剥离     • 图表书签自动生成   • 提取批注文字内容  • 跨页不切行配置     • 版本文本对比
  • 样式规则提取       • 域代码REF自动注入  • 提取被批注原文锚点 • 跨页表头重复      • 图表增删对照
  • 无损拼装合并       • GBT7714真上标角标  • 支持修订痕迹抽取   • 列宽自适应计算     • 变更说明书输出
```

#### 模块 1：高校老模板双轨剥离与装配引擎 (`template_slicer & assembler`)
- **静态页切片**：
  - 基于 XML `w:sectPr` 分节符与标题关键词（如“诚信声明”、“评阅表”、“答辩记录”）自动识别静态页面。
  - 将静态页面的 XML 节点、样式依赖、媒体关系打包缓存为不可变数据块。
- **排版样式萃取（Style Sniffer）**：
  - 自动读取模板 `word/styles.xml`，提取中文字体（宋体/黑体）、西文字体（Times New Roman）、各级标题字号与缩进磅值、行距规则，输出为标准 `style_schema.json`。
- **正文挂载与无损缝合**：
  - 将生成的正文动态段落编译为与模板样式完全对齐的 XML 节，前后无缝缝合静态页，保持模板页边距与页面设置 100% 原始一致。

#### 模块 2：真·学术交叉引用与角标编译器 (`academic_cross_ref_engine`)
- **图表自动编号与书签（Bookmarks）**：
  - 扫描论文正文结构，按章节顺序赋号（如第 3 章出现的第 1 张图赋号 `图 3-1`）。
  - 在图题注段落自动包裹 Word 书签节点：
    ```xml
    <w:bookmarkStart w:id="1001" w:name="_Ref_Fig_3_1"/>
    <w:r><w:t>图 3-1 系统总体架构图</w:t></w:r>
    <w:bookmarkEnd w:id="1001"/>
    ```
- **正文引用域代码注入（Field Codes）**：
  - 将正文中的逻辑引用标记（如 `[[REF:Fig_3_1]]`）编译为原生 Word 域：
    ```xml
    <w:fldSimple w:instr=" REF _Ref_Fig_3_1 \h ">
      <w:r><w:t>图 3-1</w:t></w:r>
    </w:fldSimple>
    ```
  - 用户在 Word 中按 `F9` 或打印时，所有引用编号联动刷新。
- **真·角标与 GB/T 7714-2015 参考文献对齐**：
  - 正文引用点包裹原生上标属性：`<w:rPr><w:vertAlign w:val="superscript"/></w:rPr>`。
  - 动态搜集全篇正文中实际引用的文献，文末按顺序自动排列参考文献列表，并使正文角标数字与文末序号严格 1:1 动态对齐。

#### 模块 3：Word 批注与修订双向提取解析器 (`comment_revision_parser`)
- **双向功能突破（解决原生只写不读的问题）**：
  - 深度遍历 `word/comments.xml`、`word/commentsExtended.xml` 与 `word/document.xml`。
  - **精确定位锚点**：通过 `<w:commentRangeStart w:id="x"/>` 到 `<w:commentRangeEnd w:id="x"/>`，精准截取**导师具体针对哪句话、哪个段落、哪个图表**提的意见。
  - 输出结构化批注列表：
    ```json
    [
      {
        "comment_id": "0",
        "author": "指导教师",
        "date": "2026-09-14T10:30:00Z",
        "anchor_text": "本系统采用单体架构进行开发",
        "comment_text": "本科毕业设计建议体现微服务划分，改成Spring Cloud",
        "location": { "chapter": 3, "section": "3.1", "paragraph_index": 2 }
      }
    ]
    ```
  - 同步提取 Word 内置的修订插入（`<w:ins>`）与删除（`<w:del>`），将导师直接在文中修改的痕迹解析为结构化变更。

#### 模块 4：中国学术规范三线表强化器 (`academic_three_line_table`)
- **解决原生三线表分页崩坏问题**：
  - 自动向每行表格注入 `<w:cantSplit/>`，禁止跨页时将一行文字截断在两页。
  - 表头行（Header Row）自动注入 `<w:tblHeader/>`，当表格跨越页面时，新页面顶部自动重现表头。
  - 自动按中英文字符宽度进行列宽等比例拟合。

#### 模块 5：语义级 Docx 差异比对分析器 (`docx_semantic_diff`)
- 对比两个版本的 `.docx`，不仅提取文字差异，更理解学术论文结构：
  - 识别出具体的章节级修改、图表增删、参考文献更新。
  - 自动输出结构化 Markdown 报告（《论文修改情况对照表》），极大减轻学生向导师汇报修改细节的负担。

## 3. Agent 创作图表/写代码工具设计（Bash 沙箱与执行环境）

### 3.1 为什么必须提供 Bash 执行环境？
在本科毕业设计中，论文内容不只是纯文字，要求有代码实现、算法推导、架构设计图、业务流程图、甚至系统真实运行界面。单纯依靠 LLM 输出文本无法完成这些多模态资产的具象化。

Agent 必须具备**自主编写代码并立即在宿主环境中执行**的能力：
1. **绘制架构图/流程图/时序图**：Agent 自主编写 Mermaid 脚本，执行 `mmdc` 命令编译输出高清 PNG 图片。
2. **绘制实验结果/数据统计图**：Agent 自主编写 Python 脚本，调用 `matplotlib` / `seaborn` / `pandas` 读取模拟数据并绘制折线图、柱状图。
3. **生成真实系统前端 UI 原型**：Agent 编写现代化 HTML/Tailwind 原型页面，调用无头浏览器（Playwright / Puppeteer）进行高分辨率页面视口渲染截图。
4. **底层文档编译与排版**：调用上述二次开发的 Python 排版脚本，解压 docx、操作 XML、打包、验证规范。

### 3.2 `bash_executor` 核心工具规格
```json
{
  "name": "bash_executor",
  "description": "在沙箱化的工作区内执行 shell/python 命令，用于运行图表渲染脚本、编译代码、生成UI截图、以及执行docx二次开发排版工具。",
  "parameters": {
    "type": "object",
    "properties": {
      "command": {
        "type": "string",
        "description": "要在工作区环境中执行的具体 shell 命令"
      },
      "work_dir": {
        "type": "string",
        "description": "命令执行的工作目录，默认为当前论文项目的 workspace 根目录"
      },
      "timeout_seconds": {
        "type": "integer",
        "description": "执行超时时间（秒），默认 60 秒，防止死循环或脚本挂死",
        "default": 60
      }
    },
    "required": ["command"]
  }
}
```

### 3.3 安全隔离与容错机制
1. **路径锁定沙箱（Path Jail）**：
   - 严格限定命令只能在当前论文工作区（`paper_workspace/`）及其预设子目录内读写，禁止跨目录访问系统敏感路径。
2. **超时强制中断（Timeout SIGKILL）**：
   - 设置最大执行时间（默认 60s），超过时间自动终止进程并释放资源，防止死循环占用。
3. **自我排错重试闭环（Self-Debugging Loop）**：
   - `bash_executor` 捕获命令的完整 `stdout`、`stderr` 和退出码（Exit Code）。
   - 一旦脚本报错（例如 Python 缩进错误、Mermaid 语法错误），错误信息立即作为 Observation 反馈给 Agent，Agent 自主阅读错误栈、修改代码并重新执行，直至产出有效资产。

## 4. Docx 版本管理系统设计（Version Management Engine）

### 4.1 设计目标
彻底终结“文件夹中充斥着几十个乱七八糟的中间临时文件”、“每次修改无法追溯改动了哪里”的混乱现状。为毕业论文建立一套轻量级、透明、**类似 Git 机制的工程化版本库（PaperVCS）**。

### 4.2 物理目录结构规范
系统实行严格的“中间产物封存、对外交付极简”原则：

```
paper_workspace/
│
├── project_meta.json                   # 项目元数据（题目、专业、技术栈、全局实体字典）
│
├── .repo/                              # 【核心版本库】内部版本快照与增量存储（隐藏目录）
│   ├── HEAD.json                       # 当前版本指针（记录当前处于哪个 commit_id）
│   ├── commits/
│   │   ├── commit_001_c1a2b3/          # 版本快照1 (v1.0 初稿)
│   │   │   ├── meta.json               # 提交信息 (版本号、时间、触发原因、总字数)
│   │   │   ├── snapshot/               # 该版本对应的章节 Markdown 源文本
│   │   │   │   ├── ch1_intro.md
│   │   │   │   ├── ch2_tech.md
│   │   │   │   └── ...
│   │   │   ├── assets_manifest.json    # 引用的所有图片、表格、UI截图哈希索引
│   │   │   └── compiled_doc.docx       # 该版本对应的完整 docx 冻结产物
│   │   │
│   │   └── commit_002_d4e5f6/          # 版本快照2 (v1.1 批注修改版)
│   │       ├── meta.json               # 明确记录：响应第3章批注
│   │       ├── parent_id               # 指向 commit_001_c1a2b3 (构建版本演进链条)
```

### 4.3 版本控制核心操作机制
1. **原子提交（Atomic Commit）**：
   - 每次创作模式生成完毕，或者编辑模式修改装配完毕，系统自动执行一次 `commit` 操作。
   - 生成唯一的短哈希（Commit ID），打上易读的版本标签（如 `v1.0`, `v1.1`）。
   - 将该版本涉及的源文本、图表清单及编译好的 docx 进行版本库归档。
2. **版本对比与差异生成（Diff & Changelog Generator）**：
   - 当从 `v1.0` 演进为 `v1.1` 时，系统自动比对两个快照的段落内容：
     - **段落级变更**：识别具体哪个自然段被重写，高亮标注删除语句与新增语句。
     - **资产级变更**：识别新增了哪张图表（如 `图 3-2`），是否有图表序号重新排布。
     - **批注响应追踪**：清晰罗列导师提出的每一条意见分别在哪个小节得到了解决。
   - 自动生成符合高校毕业答辩要求的《论文修改情况对照表 (Changelog)》。
3. **版本回滚与检出（Rollback / Checkout）**：
   - 用户在 UI 界面点击任意历史版本节点，可一键执行 `checkout`：
     - 系统自动将指针重置，工作区恢复为当时的源文件与产物状态。
     - 用户可以随时从任意历史版本重新分叉修改，绝不用担心改乱了无法恢复。
4. **时间数轴数据源绑定**：
   - 无论是 Client UI 还是 Debug UI，界面的“版本数轴”均直接通过读取 `.repo/commits/` 元数据动态渲染，实现界面视觉与底层文件版本树的 1:1 精准映射。
